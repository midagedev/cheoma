# cheoma 웹 UI 설계

목표: 첫 15초 안에 "찍어서 올리고 싶다"를 만든다. 리트윗 유발 3장치 — ① 히어로 조립 오프닝 ② 리롤의 도파민 ③ 낙관이 찍힌 사진 공유. UI 크로마는 최소화하고 씬이 주인공.

## 1. 진입 시퀀스 (히어로)

1. 로드 → 먹빛 산수 실루엣 배경 + 옅은 안개(먹안개 트랜지션 — 제거된 수묵 렌더 모드와 무관하다)
2. 지형 융기 → 기단·기둥·보·지붕 순 조립 (기존 `src/anim/assembly.js` 재사용, window 훅 経由)
3. 완성 순간 낙관 '처마' 전각이 화면 구석에 쾅 (포스트카드 낙관 재사용) + 먹 타이틀 페이드
4. 스킵: 클릭/스페이스/`?hero=0`
5. (v4 이후) 마을 전체가 안쪽→바깥쪽 스태거로 파도치듯 조립 — 집당 딜레이 0.2~0.4s

## 2. 레이아웃 (크로마) — viewport + right inspector

크롬은 성격으로 세 그룹(path / view / make+share)이며, 편집 표면은 **우측 CAD 인스펙터**가 소유한다.
전통 한지·전각 미감은 브랜드 낙관(SealLabel)에만 남기고, 편집·도구 UI는 쿨 다크 인스펙터 톤이다.

```
┌───────────────────────────────────┬────────────┐
│ 마을 › 초가            ┌─ view ─┐ │ INSPECTOR  │  좌상 path · 우상(뷰포트) view card
│                        │ ◔ dial │ │ [Explore]  │  우측 full-height dock (desktop / landscape)
│        SCENE           └────────┘ │ [Focus]    │  --inspector-w 로 dial·share 가 비킨다
│                                   │ props…     │
│ 처마 #seed   [share dock]         │ ↻ rebuild  │  뷰포트 하단 공유 독
└───────────────────────────────────┴────────────┘
```

- **데스크톱 / 태블릿 / 가로 폰**: 우측 full-height inspector column. WebGL stage is
  physically `right: var(--inspector-w)` — the camera centres on the free canvas, not
  a `setViewOffset` past an overlay. Overlay view-shift remains only for sheet/chips.
- **세로 폰**: 하단 sheet 2 detent(peek / half). focus-in 시 half 자동. 상한 `HALF_VH` → `--sheet-half`.
  Stage stays full-bleed; sheet still overlays and is measured by view-shift.
- 브레드·다이얼·독은 씬(축소된 캔버스) 위 glass chip; 만들기 패널만 opaque inspector.
- 마우스 idle 3s → `.chroma` 페이드로 씬만 남김.
- 판정: `ui-consolidation.md` §4 + `npm run check:ui-shell`.

## 3. 핵심 인터랙션

### 리롤 ("다시 짓기")
- 기존 셔플 훅 + 재조립 애니메이션. 씨앗 번호 갱신, URL `?seed=` 동기화 → 링크 공유 시 같은 마을 재현.

### 집 선택 → 파라미터 패널
- 호버: 은은한 윤곽 하이라이트(림/아웃라인). 클릭: 카메라 포커스 전환(기존 리그 재타깃) + 만들기 패널이
  집 컨텍스트로 모프(구 "우측 한지 패널" 표현은 폐기 — 패널은 좌하 하나뿐이다).
- 패널 구성 (먹선 슬라이더·도장 탭): 유형(기와집/초가) 탭 + 스키마 그룹 아코디언(평면·창호·지붕·외피·비례·마당).
  각 그룹 헤더에 커밋 대가 배지(즉시 / 놓을 때 / 마을 재생성)가 붙는다.
- 슬라이더 조작은 rAF 병합 라이브(정규 필지) 또는 놓을 때 재생성(특수 컴파운드).
- 레거시 단일건물 패널(궁·절 4종 탭, 一·ㄱ·ㄷ 확장 스테퍼, 합치기)은 **정식 폐기**됐다
  (`ui-consolidation.md` 결정 절 ④). 아래 "머지" 절과 확장 스테퍼는 역사 기록으로만 남는다.

### 머지 (합치기)
- 집(또는 채)을 선택하면 인접한 합치기 후보에 은은한 점선 윤곽 → "이웃과 합치기" 도장 버튼 또는 선택 상태에서 후보 클릭.
- 실행 시 두 매스가 서로를 향해 **두부처럼 말랑하게 끌려와** 붙고, 접합부에 새 칸·회첨 지붕이 조립되며 ㄱ/ㄷ자 큰 집으로 재편.
- 단일 필지 단계(P2)에서는 본채+부속채(행각 어휘) 사이 머지로 데모, v4 마을에서 이웃 필지 머지로 확장.
- 역방향(나누기)은 v4 백로그.

### 애니메이션 언어 — "두부 물리" (전 인터랙션 공통)
- 모든 등장·확장·머지 스텝은 **띠용띠용 탄성 이징**: overshoot(back/elastic.out 계열) + 스쿼시&스트레치 (착지 순간 y 눌림·xz 퍼짐 → 복원 출렁 1~2회).
- 기둥은 눌렸다 튀어오르고, 지붕은 안착 때 한 번 출렁, 새 칸은 두부처럼 말랑하게 자리잡음. 스텝 간 스태거로 리듬감.
- 정적·고요한 산수 화면 위에 두부 물리(귀엽고 통통)의 대비가 이 앱의 시그니처 감성 — Townscaper 계열의 만족감을 조선 미감으로.
- 구현 위치: 코어 src/anim/assembly.js 의 이징을 확장 (UI 레이어에서만 흉내내지 말 것 — 조립·확장·머지 모두 동일 언어 공유).

### 환경 다이얼 (우상)
- 링 1: 시간대 (아침·낮·석양·밤 — 돌리면 해가 실제 이동, 석양 = 골든아워 플래그십 룩)
- 링 2: 계절 (봄·여름·가을·겨울) / 링 3: 날씨 (맑음·비·눈)
- 다이얼 조작 자체가 데모 소재가 되도록 관성·스냅 감 있게.

### 사진 찍기
- 현재 앵글 → 기존 postcard 모듈로 처마 낙관을 합성 → PNG 다운로드 + Web Share API.
- 사진에 서비스의 정체성을 남기되, 장면을 가리지 않는 작은 우하단 낙관으로 절제한다.

## 4. 기술 구조

- **Svelte 5 + Vite**, `app/` 디렉토리 자립(자체 package.json). 코어는 `../src` ES 모듈 직접 import — 코어는 프레임워크 무관 유지(결정 사항).
- 기존 `index.html`+`main.js` 데모 셸은 그대로 보존 (shot 파이프라인·에이전트 검증용). SPA는 별도 엔트리로 병행하다가 배포 시 대표 엔트리 승격.
- 상태: seed·preset·time·season·weather를 URL 쿼리와 양방향 동기화.
- 기존 window 훅·URL 파라미터(조립·히어로·포스트카드·셔플) 재사용 우선, 부족한 훅은 코어에 최소 추가(단, src/ 소유권 비는 시점에).
- v4 마을 모드 통합 지점: `village` 스토어 스텁 (집 목록·선택 인덱스) — 지금은 단일 필지, v4가 채움.

## 4.5 마을 모드 ↔ 집 편집 모드 (P3 핵심 UX)

두 모드의 왕복이 앱의 척추. 판정 기준(사용자 지정): **쾌적한 왕복 · 호버가 쉽게 보이고 쉽게 잡히는 선택 · 선택 시 자연스러운 줌인 진입**.

### 모드 구조
- **마을 뷰**: 부감~사선 궤도(느린 자동 회전), planVillage 결과 전체. 우하 액션이 마을 스코프(다시 짓기=마을 리롤), 패널은 마을 옵션(규모·민촌/여염/반촌·궁·절 다이얼).
- **집 편집 뷰**: 기존 단일 카메라 리그 + 한지 파라미터 패널. 편집 결과는 마을 내 해당 필지에 반영.

### 호버 (마을 뷰)
- 픽킹은 메시가 아니라 **필지 단위 프록시(바운딩)** 레이캐스트 — 지붕·담·마당 어디를 가리켜도 그 집이 잡힘. 작은 초가도 놓치지 않게 프록시를 실제보다 살짝 크게.
- 표시: 먹선 아웃라인 + 집 전체가 아주 살짝 숨쉬듯 밝아짐 + 커서 pointer + 낙관형 미니 라벨(유형·칸수). 60fps 유지(아웃라인은 선택 프록시에만).

### 선택 → 줌인 진입
- 클릭 시 카메라가 그 집으로 **돌리-인 2~2.5초(이즈 인-아웃)**, 목표 프레이밍은 기존 단일 뷰 three-quarter와 동일 → 도착과 동시에 한지 패널 슬라이드 인. 전환 중 DoF가 서서히 조여 주변이 부드럽게 뭉개지면 시선이 집으로 모임.
- 전환 중 클릭 무시(더블 트리거 방지), ESC로 전환 중단 가능.

### 편집 → 마을 복귀
- ESC / 패널 닫기 / 줌아웃 제스처(휠) → 카메라가 마을 부감으로 되돌아감(같은 이징). 방금 편집한 집이 잠깐 은은히 하이라이트되어 "내 집이 저기" 앵커 유지.

### 성능 전제
- 마을 뷰 실시간 60fps: 집 프로토타입 서브지오메트리 InstancedMesh 병합(수십 채→수 드로우), 호버 아웃라인은 프록시 1개 대상. capital 75호가 기준선.

## 4.6 최초 안정 장면 조작 안내

첫 방문자는 Hero와 마을 전환이 끝난 첫 안정 프레임에서만 작은 `SceneGuide`를 본다. 안내는 씬 위를 덮는
투어나 모달이 아니라 한지 카드 한 장이다. 데스크톱은 드래그 궤도·휠 줌·집 선택·`Esc`/둘러보기 복귀를,
터치는 한 손가락 궤도·두 손가락 줌/팬·집 탭·둘러보기 복귀를 실제 제품 입력과 같은 말로 설명한다.

- 표시 정책은 `app/src/lib/scene-guide.js`의 순수 함수가 소유한다. `unseen + village scene + stable`일 때만
  보이고 Hero, landing, wave, veil, cinematic, References, toast 중 하나라도 활성화되면 숨는다.
- 컴포넌트 root는 `pointer-events: none`이다. 최소 `44×44px`인 명시적 닫기 버튼만 입력을 받으며
  autofocus, focus trap, scrim, timeout, 카메라 이동을 만들지 않는다.
- App은 `.app-surface` 안에 컴포넌트를 두어 References 모달의 `inert` 경계를 그대로 상속한다. 첫 실제
  canvas `pointerdown`/`wheel` 또는 닫기에서 정책의 `dismiss()`를 호출하되 원래 이벤트를 취소하거나
  전파 중단하지 않는다.
- 방문 기록은 URL/share 상태와 분리된 `cheoma-scene-guide-v1` localStorage 한 항목이다. 읽기 실패는
  unseen으로 취급하고, 쓰기 실패여도 현재 세션에서는 즉시 사라진다. 로케일 변경은 방문 기록을 초기화하지 않는다.

## 4.7 키보드 건물 탐색

포인터로 필지를 집기 어려운 사용자는 `ContextPanel` 공통 헤더의 네이티브 건물 선택기와 명시적
보기/이동 버튼으로 같은 마을 카메라 경로를 쓴다. 캔버스에 `role="application"`이나 Arrow/WASD
키맵을 만들지 않는다. 후보는 엔진의 기존 pick proxy stable ID에서 `{id,type}`만 받아오며 UI가 plan,
Object3D, 바운드나 별도 장면 모델을 소유하지 않는다.

- option 변경은 목적지만 고르고 카메라를 움직이지 않는다. 버튼 활성화만 aerial `focus(id)` 또는
  focus `switchTo(id)`를 호출한다.
- 선택기는 마을/집 morph owner 밖에 상주한다. 전환 중 버튼은 `aria-disabled`와 실행 guard로 중복을
  막되 포커스와 native select를 보존한다.
- 현재 건물은 도착 `villageSelect`에서만, 둘러보기는 도착 `villageReturnDone`에서만 live region에
  반영한다. 출발 이벤트를 현재 위치로 읽지 않는다.
- References의 기존 app-surface `inert`, cinematic 패널 은닉, wave 잠금을 그대로 상속한다.
- reduced motion은 카메라 API를 우회하지 않고 공통 tween을 첫 렌더 프레임에 끝낸다. 시작과 완료를
  같은 입력 호출 스택에서 동기 발생시키지 않는다.
- #158 P8: 선택기는 랜드마크(종가·관아·궁·절) 전부와 일반 집 최대 20채를 `optgroup` 으로 그룹핑해
  렌더한다(한양 297 옵션 평면 나열이 감사 대상 결함이었다). **남은 한계** — 21번째 이후의 일반 집은
  이 경로로 도달할 수 없다. 선택된 대상은 상한을 넘어도 항상 목록에 들어가지만, 목록에 없는 집을
  고를 수는 없다. 상한은 B안의 결정이므로 유지하되, 그룹 내 페이징·구역별 하위 그룹이 후속 후보다
  (`ui-consolidation.md` §6.5).

세부 데이터·검증 계약은 [`building-navigation.md`](building-navigation.md)에 있다.

## 4.8 진입 반응성 (#16)

타이틀의 "들어가기"는 방문자가 처음 만지는 표면이다. **누름은 그 프레임에 확인돼야 하고, 남는 대기는
명시적으로 보여야 한다.** 사용자 지시(2026-07-25): "누르면 아무 반응없이 몇초 기다리다가 진입이 되는데
기다려야만 하는 부분이 있다면 명시적으로 스피너를 써줘. 물론 기다리지 않아도 되도록 성능 최적화하는 게 최고".

- **원인(실측)**: 클릭 핸들러가 곧바로 `engine.village.enterHero()` 를 부르고, 그 안의 `buildVillage(sync)`
  는 사전 생성 캐시가 없으면 마을 전체를 **메인 스레드에서 동기로** 짓는다. 같은 태스크라 브라우저는
  그동안 한 프레임도 칠하지 못한다 — 타이틀 자신의 페이드조차. chromium 실측: 동기 핸들러 731~820ms,
  클릭 후 첫 rAF 1.7~3.2초, **6초 동안 프레임 2개**.
- **계약**: ① 누름 즉시 `heroEntering` 을 세워 눌림·진행 표시를 칠하고 **페인트를 한 번 양보**한다.
  ② 사전 생성이 진행 중이면 `village.isReady()` 가 참이 될 때까지 프레임 단위로 기다린다 — 워커·rAF
  청킹이라 **동기 빌드보다 빠르고**, 기다리는 동안 타이틀이 살아 있어 진행 표시가 돈다.
  ③ 그 다음 진입한다. 캐시 hit 경로만 남으므로 스왑이 즉시이고 타이틀 페이드도 정상 재생된다.
  상한(`ENTRY_PREGEN_WAIT_MS`)을 넘기면 그대로 진입한다 — 무한 대기는 금지.
- **표시**: 진행 표시는 한지 위 **먹선 한 획**(`[data-entry-progress]`)이다. 문구 깜박임을 멈추고
  획만 미세하게 흐른다 — 상시 결정("모션은 미세 스케일, 눈에 띄면 과한 것")과 스피너가 로딩 구간의
  주인공이 되지 않아야 한다는 제약을 함께 지킨다. `prefers-reduced-motion` 에서 주기를 늘린다.
- **이것은 이벤트 순서 계약이다.** 헤드리스 절대 ms 는 판정 근거가 아니므로 게이트는 "핸들러가 메인
  스레드를 즉시 반납하는가 / 누른 직후 프레임을 그릴 수 있는가 / 첫 프레임에 `aria-busy` 와 진행
  표시가 있는가 / 타이틀이 씬 준비 전에 사라지지 않는가"만 본다 — `npm run check:entry`
  (`tools/check-entry-responsiveness.mjs`). 이 경로는 그 전까지 **게이트 커버리지가 0** 이었다
  (`check:app` 은 `?hero=0` 으로 부팅하고, `.hero` 를 누르는 유일한 도구는 없는 `dist-entry` 빌드를
  요구했다) — 같은 회귀가 두 번 통과한 이유다.
