# 모바일 효과 축소 전수 감사 (2026-07-25)

상태: **조사·분류·복원 계획 완료 / 구현 미착수**. 이 문서는 자립형이다 — 판정 근거·측정치·복원 절차가 모두 여기 있다.

## 1. 왜 이 감사를 했나

앱에는 "모바일이니까 줄인다"는 분기가 24곳 있다. 그중 상당수는 저장소 초기 임포트(`e75298b`, 2026-07-18) 때
들어왔고, 그 뒤 성능 여유를 크게 늘린 개선들(프레넬 림이 RimPass를 대체해 부감 +6601 → +1 드로우콜,
#131 눈 흰틴트가 적설 볼륨 시뮬을 전면 제거, #123 숲 크런치 워커 오프로드, #140/#148 병합)은 그 분기들을
재검토하지 않았다. 게이트 중 일부는 **도입 당시의 근거가 이미 소멸**했고, 하나는 `docs/look-grammar.md` §5
("성능을 이유로 통합자(림·헤이즈·fog·DoF)를 끄는 것 — 통합자는 이 앱의 본체다. 비용은 다른 곳에서 줄인다")를
정면으로 위반한다.

## 2. 검증 방법과 한계

- 정본 커밋: **`142d637`**. 본체 작업 트리는 다른 에이전트가 수정 중이므로 `git archive 142d637`로 뜬 고정
  스냅샷에서만 브라우저 검증했다(전용 vite 127.0.0.1:4521, 전용 cacheDir).
- A/B는 **같은 뷰포트·같은 DPR·같은 씬**에서 게이트만 뒤집어 비교했다. 스냅샷 사본의 `device.svelte.js`에
  `?fxperf=0|1` / `?fxcompact=0|1` 오버라이드를 임시로 넣었다(스크래치 전용, 저장소 미반영). 구현 라운드에서
  같은 A/B를 다시 하려면 이 오버라이드를 **정식 검증 훅으로 승격**하는 것이 좋다.
- 기준 프레임: `?hero=0&village=1&worker=0&shot=1&vscale=capital&vseed=7` + `p31` focus — `check:cinematic:app`과
  `shoot-focus-level`이 이미 쓰는 결정론 케이스.
- 디바이스: iPhone 15급 에뮬레이션(393×852 CSS, DPR 3, touch) vs 데스크톱(1440×900, DPR 2).
- **헤드리스 절대 ms는 근거로 쓰지 않았다.** 헤드리스 ANGLE은 셰이더 링크를 직렬화해 절대 시간이 부풀고,
  모바일 GPU의 체감은 데스크톱 헤드리스로 재현되지 않는다. 대신 **픽셀 수·텍셀 수·프로그램 개수·인스턴스
  수·텍스처 메모리** 같은 구조적 비용으로 논증한다.

이 표의 첫 두 줄이 이 감사의 핵심이다. **게이트를 전부 풀어도 폰은 데스크톱의 25.8% 픽셀만 칠한다**(현행은
14.5%). 즉 픽셀 예산 관점에서 폰에는 아직 3.9배의 여유가 있다 — 이것은 강한 사전 확률이지, 픽셀당 성능이
다른 모바일 GPU에서의 증명은 아니다(§7). 반대로 히어로 줄은 가장 나쁜 종류의 축소를 보여준다 —
**길이는 8.1초 그대로인데 이동 거리만 1/3로 줄어** 폰 사용자는 8초 동안 거의 정지한 카메라를 본다.
짧게 끝나 이득을 보는 것도 아니고, 그 대가로 아낀 GPU 비용은 0이다(카메라 키프레임 산술).

### 2.2 관찰된 시각 차이 (단일축 분리)

같은 프레임(capital/7/p31, 가을·석양 고정)에서 축을 하나씩만 뒤집어 처마·용마루를 확대 비교했다.

- **pixelRatio만 1.5 → 2** (`fxcompact=0`): 용마루 위 적새 하이라이트가 현행에서는 **끊어진 흰 점열**로 깨지고,
  기와 골 사이 선과 서까래 끝단이 계단화된다. PR 2에서는 같은 선이 연속선으로 읽히고 뒤편 나무 실루엣의
  들쭉날쭉함도 사라진다. 이 앱의 주제 자체가 1픽셀 근방의 얇은 선(처마선·용마루·기와 골)이라, 해상도 하향은
  다른 어떤 효과보다 직접적으로 주제를 깎는다.
- **DoF만 ON** (`fxperf=0`, PR은 1.5 그대로): 부감은 픽셀 불변(양쪽 모두 `dofAmount=0`), 근접에서만 달라진다.
  현행은 뒷산 나무가 지붕과 **똑같이 선명해** 기와 골·서까래가 나뭇잎 다면체와 경쟁하고, 프레임 전체가 한 장의
  평평한 선명면이 된다. DoF를 켜면 배경이 물러나 집이 분리되고, **부수적으로 저폴리 나무의 각진 면이
  가려진다** — DoF를 끈 대가로 폰에서는 나무 지오메트리의 다면체가 더 드러나 보인다.

## 3. 분류 기준

- **(필수)** 실제 모바일 GPU/메모리 제약. 픽셀·텍셀·메모리·메인스레드 연산 수로 근거를 댄다.
- **(복원 후보)** 예방적이거나 근거가 소멸. look-grammar §5에 걸리는 항목은 자동으로 여기.
- **(실기기 확인 필요)** 헤드리스로 판단 불가. 위험도와 확인 절차를 명시한다.

P1/P2의 옳은 축은 뷰포트 CSS 크기가 아니라 **실제 픽셀 예산과 GPU 성격**이다. 권고:

```js
// 제안 형태 (구현 라운드에서 확정)
const backingPixels = w * h * Math.min(devicePixelRatio, 2);   // 상한 적용 후 실제 칠할 픽셀
device.phone   = device.touch && Math.min(w, h) <= 520;        // 진짜 폰만
device.perf    = device.phone;                                  // 좁은 데스크톱 창은 제외
device.compact = backingPixels > 2.2e6 && device.phone;         // 픽셀 예산으로만 하향
```

이렇게 하면 좁은 데스크톱 창과 태블릿이 게이트에서 빠지고, 폰도 픽셀 예산이 실제로 클 때만 하향된다.

## 8. 게이트·회귀 주의

- `tools/check-cinematic-reveal-app.mjs:1179`의 `mobile.motion === 'compact'` 단정은 **R1과 함께 반드시 갱신**해야
