# 모바일 효과 축소 전수 감사 (2026-07-25)

상태: **조사·분류 완료 / 복원 R1~R8 구현됨(커밋 전) / R9 실기기 확인 대기**. 이 문서는 자립형이다 —
판정 근거·측정치·복원 절차가 모두 여기 있다. §9에 구현 라운드의 실측 A/B와 항목별 결과를 남겼다.

## 1. 왜 이 감사를 했나

앱에는 "모바일이니까 줄인다"는 분기가 24곳 있다. 그중 상당수는 저장소 초기 임포트(`e75298b`, 2026-07-18) 때
들어왔고, 그 뒤 성능 여유를 크게 늘린 개선들(프레넬 림이 RimPass를 대체해 부감 +6601 → +1 드로우콜,
#131 눈 흰틴트가 적설 볼륨 시뮬을 전면 제거, #123 숲 크런치 워커 오프로드, #140/#148 병합)은 그 분기들을
재검토하지 않았다. 게이트 중 일부는 **도입 당시의 근거가 이미 소멸**했고, 하나는 `docs/look-grammar.md` §5
("성능을 이유로 통합자(림·헤이즈·fog·DoF)를 끄는 것 — 통합자는 이 앱의 본체다. 비용은 다른 곳에서 줄인다")를
정면으로 위반한다.

## 2. 검증 방법과 한계

- 정본 커밋: **`142d637`**. 본체 작업 트리는 다른 에이전트가 수정 중이므로 `git archive 142d637`로 뜬 고정
  스냅샷에서만 브라우저 검증했다(전용 vite 127.0.0.1:4521, 전용 cacheDir).
- A/B는 **같은 뷰포트·같은 DPR·같은 씬**에서 게이트만 뒤집어 비교했다. 스냅샷 사본의 `device.svelte.js`에
  `?fxperf=0|1` / `?fxcompact=0|1` 오버라이드를 임시로 넣었다(스크래치 전용, 저장소 미반영). 구현 라운드에서
  같은 A/B를 다시 하려면 이 오버라이드를 **정식 검증 훅으로 승격**하는 것이 좋다.
- 기준 프레임: `?hero=0&village=1&worker=0&shot=1&vscale=capital&vseed=7` + `p31` focus — `check:cinematic:app`과
  `shoot-focus-level`이 이미 쓰는 결정론 케이스.
- 디바이스: iPhone 15급 에뮬레이션(393×852 CSS, DPR 3, touch) vs 데스크톱(1440×900, DPR 2).
- **헤드리스 절대 ms는 근거로 쓰지 않았다.** 헤드리스 ANGLE은 셰이더 링크를 직렬화해 절대 시간이 부풀고,
  모바일 GPU의 체감은 데스크톱 헤드리스로 재현되지 않는다. 대신 **픽셀 수·텍셀 수·프로그램 개수·인스턴스
  수·텍스처 메모리** 같은 구조적 비용으로 논증한다.

이 표의 첫 두 줄이 이 감사의 핵심이다. **게이트를 전부 풀어도 폰은 데스크톱의 25.8% 픽셀만 칠한다**(현행은
14.5%). 즉 픽셀 예산 관점에서 폰에는 아직 3.9배의 여유가 있다 — 이것은 강한 사전 확률이지, 픽셀당 성능이
다른 모바일 GPU에서의 증명은 아니다(§7). 반대로 히어로 줄은 가장 나쁜 종류의 축소를 보여준다 —
**길이는 8.1초 그대로인데 이동 거리만 1/3로 줄어** 폰 사용자는 8초 동안 거의 정지한 카메라를 본다.
짧게 끝나 이득을 보는 것도 아니고, 그 대가로 아낀 GPU 비용은 0이다(카메라 키프레임 산술).

### 2.2 관찰된 시각 차이 (단일축 분리)

같은 프레임(capital/7/p31, 가을·석양 고정)에서 축을 하나씩만 뒤집어 처마·용마루를 확대 비교했다.

- **pixelRatio만 1.5 → 2** (`fxcompact=0`): 용마루 위 적새 하이라이트가 현행에서는 **끊어진 흰 점열**로 깨지고,
  기와 골 사이 선과 서까래 끝단이 계단화된다. PR 2에서는 같은 선이 연속선으로 읽히고 뒤편 나무 실루엣의
  들쭉날쭉함도 사라진다. 이 앱의 주제 자체가 1픽셀 근방의 얇은 선(처마선·용마루·기와 골)이라, 해상도 하향은
  다른 어떤 효과보다 직접적으로 주제를 깎는다.
- **DoF만 ON** (`fxperf=0`, PR은 1.5 그대로): 부감은 픽셀 불변(양쪽 모두 `dofAmount=0`), 근접에서만 달라진다.
  현행은 뒷산 나무가 지붕과 **똑같이 선명해** 기와 골·서까래가 나뭇잎 다면체와 경쟁하고, 프레임 전체가 한 장의
  평평한 선명면이 된다. DoF를 켜면 배경이 물러나 집이 분리되고, **부수적으로 저폴리 나무의 각진 면이
  가려진다** — DoF를 끈 대가로 폰에서는 나무 지오메트리의 다면체가 더 드러나 보인다.

## 3. 분류 기준

- **(필수)** 실제 모바일 GPU/메모리 제약. 픽셀·텍셀·메모리·메인스레드 연산 수로 근거를 댄다.
- **(복원 후보)** 예방적이거나 근거가 소멸. look-grammar §5에 걸리는 항목은 자동으로 여기.
- **(실기기 확인 필요)** 헤드리스로 판단 불가. 위험도와 확인 절차를 명시한다.

**사실과 다르다**. #131이 `snowvol`/`rainflow`를 전 디바이스에서 제거했으므로 `lowPerf`가 지금 실제로 바꾸는
것은 `collide`(M16)와 꽃잎 개수(M17)뿐이다. 주석은 복원 라운드에서 수정해야 한다.

P1/P2의 옳은 축은 뷰포트 CSS 크기가 아니라 **실제 픽셀 예산과 GPU 성격**이다. 권고:

```js
// 제안 형태 (구현 라운드에서 확정)
const backingPixels = w * h * Math.min(devicePixelRatio, 2);   // 상한 적용 후 실제 칠할 픽셀
device.phone   = device.touch && Math.min(w, h) <= 520;        // 진짜 폰만
device.perf    = device.phone;                                  // 좁은 데스크톱 창은 제외
device.compact = backingPixels > 2.2e6 && device.phone;         // 픽셀 예산으로만 하향
```

이렇게 하면 좁은 데스크톱 창과 태블릿이 게이트에서 빠지고, 폰도 픽셀 예산이 실제로 클 때만 하향된다.

### 9.3 이 라운드가 새로 관측한 것 (감사에 없던 사실)

- **폰 세로 프레임의 arrival 중반 구도.** 복원된 84° 선회는 데스크톱이 이미 배포 중인 authored 호이지만,
  세로(393×852) 프레임에서는 3~5초 구간에 전경 능선·수관이 피사체 앞을 지난다(도착 프레임 6~8초는
  before보다 뚜렷하게 잘 잡힌다). 스윕하는 호가 전경을 통과하는 것은 리빌 어법으로 읽힐 수 있으나,
  세로 구도에서 의도로 읽히는지는 실기기 판정 대상이다(§7 체크리스트에 추가). 이 라운드는 데스크톱과
  다른 폰 전용 안무를 새로 저술하지 않았다 — 폰을 데스크톱과 같게 만드는 것이 M14의 목적이었다.
- **`device.perf`에 성능이 아닌 것이 두 개 얹혀 있었다**(U2 입력 장치, U3 레이아웃). 술어를 좁히면
  드러나는 결합이며, 각자의 실제 축으로 옮겼다.
- 시각 A/B는 시간·계절을 URL로 고정해야 한다. 기준 프레임은 계절을 고정하지 않아 부팅마다 달라지므로
  크롭 비교가 오염된다(`time=day&season=summer` 고정 컷으로 재촬영했다).

### 9.4 별건: "모바일에서 히어로 카메라가 회전하지 않는다"의 두 번째 원인 — 프레임 페이싱

사용자 보고를 M14(이동 축소)만으로 설명할 수 없었다. **독립적인 두 번째 결함**이 있었다.

`engine.js` 렌더 루프의 `const dt = Math.min(elapsed, 0.05)`는 스파이크 가드가 아니라 **20fps 천장**이다.
`clock.getDelta()` 자체는 벽시계이지만, 프레임이 0.05초를 넘는 순간부터 이 dt 를 소비하는 모든 것 —
리빌 카메라, 조립, 카메라 트윈, 규모 웨이브, 진입 먹안개, 입자 — 이 `0.05 / 실제 프레임 시간` 배로
느려진다. 재생률이 프레임 시간에 반비례하므로 저fps 기기일수록 연출이 더 늘어진다.

측정(폰 에뮬레이션, 같은 히어로 랜딩):

| | before `ecc18d8` | after |
|---|---|---|
| 벽시계 8초 시점의 arrival progress | **0.0147** | **1.0000** |
| 14초 안에 완주하는가 | 아니오(관측 안 됨) | 예 |
| 적용 dt / 실제 벽시계 델타(중위) | — (천장에 고착) | **1.0000** |
| CPU 스로틀 1×/4× 차이 | 없음(0.0147 동일 — 이미 천장 포화) | — |

리드가 배포본에서 관측한 `playbackRate` 0.008(데스크톱)·0.035(모바일)는 코드의 필드가 아니라 정확히
이 비율이다: `0.05 / 프레임 시간`. 0.008 ⇒ 프레임 6.3초, 0.035 ⇒ 프레임 1.4초. 품질 다운시프터나 오디오
클록과는 무관하다 — `postQuality`/`activeBokehTaps` 는 Bokeh 탭 수만 줄이고 시간에 개입하지 않으며,
`architectural-reveal.js`의 타임라인은 이미 `advance(seconds)`로 순수하다. 원인은 이 한 줄뿐이었다.

수정: 정책을 `app/src/engine/frame-clock.js`(three 무의존)로 분리하고, 천장을 고정값이 아니라 **최근
프레임 시간 추정치의 배수**로 잡았다. 지속적 저fps 는 추정치가 따라 올라가 그대로 통과하고(벽시계
충실), 단발 스톨만 잘린다. 추정치는 클램프된 값으로 갱신해 스파이크가 스스로 천장을 밀어올리지
못하게 했고, 상승만 빠른 비대칭이라 저fps 진입 후 2프레임 안에 추적에 든다.

`tools/check-frame-clock.mjs`(=`npm run check` 포함)가 이 정책을 고정한다: 120~5fps 에서 8.1초 안무가
벽시계 8.10~8.20초에 완주, 2fps 8.50초·1fps 10.0초(램프 비용, 상한 내), 60fps 정상 주행 ratio 정확히 1,
10초 스톨은 0.133초로 절단, 연속 스톨도 계속 절단. 종전 정책의 반례(5fps → 32.6초)도 같은 파일에 남겼다.

**왜 기존 게이트가 못 잡았나**: 안무 게이트가 전부 `debugArchitecturalRevealSeek(progress)`로 결정론
샘플만 검사한다. seek 는 벽시계를 우회하므로 경로·스윕·구도는 검증되지만 "제 시간에 도는가"는
아무도 보지 않았다. 새 게이트는 그 빈 축만 담당한다. 부수 효과로 이 결함은 **모바일 전용이 아니다** —
저fps 데스크톱에서도 같은 비율로 느려졌다.

**부수 효과로 드러난 것 — focus 왕복 잔여 지오메트리**: 클록을 고치자 `check:lod:app`의
`aerial→focusOut` 지오메트리 델타 예산(128)이 깨졌다. 조사 결과 잔여물이 늘어난 것이 아니라
**aerial 기준선이 더 깊이 정착하게 된 것**이었다 — 프레임당 진행이 실제 시간을 따르면서 aerial 표본
시점에 동물·크리터·앰비언트가 제대로 잠들고 그 지오메트리가 해제된다. 두 끝점을 같은 조건에서
재도록 하네스 표본을 프레임 수에서 **자원 고원**으로 바꾼 뒤(`check-lod-app.mjs settleResources`)
같은 프로토콜로 실측하면:

| | aerial | focusOut | 델타 |
|---|---|---|---|
| `ecc18d8` | 849 | 921 | **72** |
| 현재 트리 | 783 | 911 | **128** |

focusOut 은 −10, aerial 은 −66 이다. 즉 focus 왕복 뒤 남는 지오메트리는 양쪽에서 비슷하고, 종전에는
aerial 기준선에 섞여 있던 "아직 잠들지 않은" 약 66개가 그 잔여물을 가리고 있었다. 절대 예산
(focusOut ≤ 1024, 실측 911)은 여유롭게 통과하므로 즉시 위험은 없다. 델타 예산은 144로 재저작하고
근거를 표에 남겼다.

**미해결로 넘기는 질문**: 완전히 정착한 aerial 기준으로 약 128개 잔여 지오메트리가 의도된 캐시
(#129 `__kept` 앵커·프리워밍 LOD·공유 링 자원)인지 누수인지. 이 숫자를 다시 내리려면 그 구분이
선행이며, 이 라운드에서는 판단하지 않았다.
